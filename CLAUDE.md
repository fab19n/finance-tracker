# Money Tracker - notes for working on this repo

Local-first personal finance tracker (MYR). Next.js 16 (App Router, **Cache Components on**) + SQLite (better-sqlite3) + Drizzle + Tailwind + Recharts + Vitest.
`AGENTS.md` says this is not the Next.js you know: read `node_modules/next/dist/docs/` before writing Next-specific code.

## Commands

**pnpm only** (no `package-lock.json`; the lockfile is `pnpm-lock.yaml`).
`pnpm dev` · `pnpm test` (~730 tests, a few seconds) · `pnpm lint` · `pnpm run build` · `pnpm run seed:demo` (writes `data/demo.db`) · `pnpm run db:generate` (after editing `src/db/schema.ts`).
A production build (`pnpm build`) and `pnpm dev` don't clash (dev writes to `.next/dev`), so the phone server (`pnpm start:phone`, port 3100) can run beside the user's dev server. A SECOND dev server, or a throwaway build for a test, needs `NEXT_DIST_DIR=.next-test` (read by `next.config.ts`) and another port. Undo its side effects afterwards: Next adds that folder to `tsconfig.json` (restore with `git show HEAD:tsconfig.json > tsconfig.json`) and points the git-ignored `next-env.d.ts` at it (put it back to `./.next/dev/types/...`); then delete the folder. Don't stop a server you didn't start; on Windows, stopping the shell wrapper leaves the Node child listening, so check the port and stop that PID (after reading its command line).
**Supply-chain policy (pnpm 11):** dependency install scripts are denied via `allowBuilds` in `pnpm-workspace.yaml` (none are needed: better-sqlite3 ships prebuilt binaries), and pnpm refuses versions published within its `minimumReleaseAge`. If pnpm ever wants to add a `minimumReleaseAgeExclude` entry, don't accept it silently: lower the version range in `package.json` to an older release instead (this happened with `lucide-react`).
Run against a throwaway DB: `$env:DB_PATH="data/demo.db"; pnpm dev`. Never point tests or demos at `data/finance.db`.

## Rules that are easy to break

- **A new migration reaches a RUNNING `pnpm dev` only when something opens the database again.** The dev server keeps its first connection (cached on `globalThis`), so the moment the code names a new column, every query that selects it fails until the migration has run. After generating one (`pnpm exec drizzle-kit generate --name=...`), back up (`pnpm run backup`) and apply it at once to the real file with any script that calls `openDb()` (it migrates), then check row counts and sums are unchanged. Additive migrations only (a column, an index); nothing the old code can't read.
- **Money is integer sen.** Convert only through `src/lib/money.ts` (`parseSen`, `formatRM`). Never store or add floats.
- **All DB access goes through `getDb()`** (`src/db/client.ts`). With Cache Components, a synchronous better-sqlite3 query is a "predictable value" and gets *prerendered at build time*; `getDb()` calls `await connection()` first to force request-time. It also enforces the optional PIN lock (`requireAuth`). Don't open the DB any other way in app code.
- **Drizzle query builders are thenable.** Returning one from an `async` function executes it. Keep builder helpers synchronous (see `baseSelect` in `src/lib/queries/transactions.ts`).
- **Every route needs a Suspense boundary *below* the shared layout**, or `next build` fails / dev shows "blocking route". Each route folder has a one-line `loading.tsx`; a page that reads `searchParams` outside `(app)` needs its own `<Suspense>` (see `src/app/login/page.tsx`). `usePathname()` in client nav is wrapped in `<Suspense>` too.
- **`var()` does not work in SVG presentation attributes** (`fill="var(--x)"` renders black). Chart colours live in CSS classes in `globals.css` (`.viz-line-*`, `.viz-bar-*`); components set `className`, not colours. Palette = dataviz slots 1-3: spending/needs blue, income/saved aqua, wants/comparison orange, de-emphasis gray.
- **Transfers are neither income nor spending.** An investment is an account of type `investment`; contributing is a transfer. Analytics read `listFlowRows` which excludes transfers.
- Balances are always derived from transactions (`getAccountBalances`), never stored.
- `middleware.ts` is now `src/proxy.ts`.

## Pay cycles, bills and the savings flow (`src/lib/plan`)

- The user's month runs **payday to payday**, not calendar month. Cycles come from Salary income (`cycle.ts`); the next payday is predicted from the median day-of-month. The Plan page, the leak detector's savings findings and (by default) the **Dashboard** use cycles. The Dashboard's analytics (`analytics/summary.ts`) are all keyed on a calendar month `YYYY-MM` and a day-of-month, so cycle view does NOT change them: `analytics/periods.ts` (`payCyclePeriods`, `rekeyRows`) re-files each entry under the month its cycle is NAMED after (the one holding its middle day: 26 Sep - 25 Oct is October) with the day counted from payday (capped at that month's length), and the page then runs the same functions. Cycle boundaries: the Plan's own `currentCycle` for the one in progress, consecutive recorded salaries for past ones, and before the first recorded salary one cut a month at the median day of the last three recorded paydays (not the stale Settings day). The page picks cycles when a salary has been recorded recently (`currentCycle().source === "salary"`), else calendar months; `?view=cycle|month` overrides and is carried by the month links. `paycheckIn(income, expected)` (a tenth of the expected pay, or RM 5) decides "no pay yet": RM 0.11 of GO+ interest once defeated the old `income === 0` test and showed a red "Overspent ... -2461200% of income".
- Accounts have a `purpose` (`spending` | `savings`), exclusive per role (`saveAccount`). Plan features need the spending account to be set; they degrade to a prompt in the UI when it isn't.
- `recurring_bills` are matched to transactions by `billId` (set by "mark paid") or by description (`descriptionMatchesBill`): bill **keywords match as substrings, the bill name only as a whole word** (a rent bill must not match "PARENTS"). A bill amount may be a range (min/max); totals use the midpoint, "safe to spend" uses the max.
- `savings-flow.ts` splits money drawn from savings into a **planning gap** (the payday split left too little for the bills: `min(drawn, max(0, billsFromSpending - leftAfterDeposit))`) and **everyday-from-savings** (the rest). The planning gap is never presented as a saving; only the everyday part is.
- **Bills paid straight from the savings account never needed a top-up**, so only `billsFromSpending` (bills paid from the spending account) counts toward the planning gap. That money is reported separately as `spentFromSavings` (+ `savingsSpendTop`, the biggest categories) and drives the `savings_spending` finding, which claims no saving: it is spending paid from the wrong place.
- `paydayDeposit` = transfers to savings in the cycle's first 7 days (all of them if none fell there). "What you usually move" averages that, so a one-off transfer mid-cycle (e.g. a final payslip) doesn't inflate it. A cycle in progress counts as soon as its payday move exists.
- `detectLeaks` takes `billItems` (registered bill names); those are planned spending, so they're never a "spike" or a "habit".
- Transfers stay out of income/spending everywhere; the leak detector reads `plan.flows` for the savings findings.

## Shared bills (`src/lib/plan/shares.ts`, `src/lib/queries/shares.ts`, `src/app/actions/shares.ts`, `/plan/shared`)

- `bill_shares` = one row per person per bill (`share` sen per month, `startMonth`, optional `endMonth`, `matchKeywords`). A payment from them is an **income** transaction with `transactions.share_id` set (and the *Reimbursements* category). No separate payments table. **Two ways to split a bill** (`recurring_bills.sharing`): `monthly` (above: every person owes `share` for every charged month, payments fill the oldest months) and `turns` (Spotify: ONE person pays the whole month, rotating; you take the first month of each six-month cycle). Turns live in `bill_turns` (one row per bill + month; `share_id` NULL = you) and `rotationLedger` (`lib/plan/shares.ts`) applies each person's payments to THEIR OWN turns oldest first (a turn costs what the bill was charged that month; within `TURN_TOLERANCE` = RM 1.00 counts as paid; money no planned turn takes is `unmatched`, never spread over other months). Using the monthly model for a rotating bill was the original mistake: it read each RM 30.90 as six months of RM 5.15 and showed people "paid ahead" for turns they had only just settled. Months are NOT assigned in a fixed order nor by payment order (in a real cycle one friend paid first but another had taken the earlier month): a month with no `bill_turns` row is OPEN until someone says they will cover it. A payment with no unsettled turn to land on is a `leftovers` entry on that person, shown as "which month did they cover?" with a one-tap `coverMonth` (refuses a month somebody already has); never auto-assigned. A month that is YOURS and was charged (`Rotation.charged`) is shown as paid. `setSharing` switching to turns also sets each person's `share` to the whole bill (that is what a payment from them is expected to be, and what `pickShare` divides by).
- **The model:** a person owes `share` for every calendar month from `startMonth` to the latest month the bill was charged (`owedMonths`; gaps are filled, so a late-posting charge or a payment covering pre-data months still works), and their payments, summed, are applied to their OLDEST months first (`personLedger`). Lump sums, prepayment (`paidThrough` runs into future months) and part-payments all fall out of that one rule. Pure and tested (`tests/shares.test.ts`); don't add per-month payment rows.
- `pickShare` decides who sent a line: keywords match anywhere, a name only as whole words; if two people match, the one whose share divides the amount wins, else nobody (left in the "not yet counted" list rather than guessed). The classifier calls it for money in (`source: "share"`, after learned rules, before bills); `commitRows` stores `shareId` only for income. `saveShare` also claims past unassigned money-in that clearly belongs to that person.
- Deleting a bill or a person must null `transactions.share_id` first (foreign keys are enforced). "Not yet counted" only offers amounts between one smallest share and a year of the largest, so KWSP credits and the like never appear.

## Bank statement import (`src/lib/import`, `src/app/actions/import.ts`)

- Pipeline: PDF (`unpdf`, positioned text items grouped into lines) / CSV / pasted text -> `ParsedRow[]` -> `checkBalances` -> `classifyRows` -> review UI -> `commitRows`. Everything runs server-side in-process; nothing is sent anywhere. PDF passwords are used once and never stored.
- **The balance chain is the safety net**: previous balance + amount must equal the printed balance. It repairs in/out signs, reports mismatches, and only claims `openingVerified` when the statement states an opening balance. Never import rows the check rejects silently; surface them.
- Classification order: duplicate -> learned rule (`import_rules`) -> shared-bill payer -> recurring bill -> **history** -> built-in merchant rules -> salary guess -> default. *History* (`history.ts`, `learnFromHistory`) is the user's own imported entries: a payee (`rulePattern` group) filed under ONE category at least twice, never transfers, bill-linked or share-linked lines, never hand-typed entries (no `importKey`). It exists because accepting a proposal unchanged never saves a rule (only corrections do), so an accepted payee was flagged again every month. Any disagreement among past entries means "ask again", not "pick the commonest". **Never learned or applied for a name that also appears on a transfer** (`learnFromHistory` drops patterns used by any imported transfer; `classifyRows` skips history when a transfer rule knows the name): on the statement a transfer rule points back at, step 2 skips that rule, and without this guard the line fell through to history and was saved as spending next to the real transfer (double-counted). Built-in food names match as PREFIXES (`restoran\w*`, `warung\w*`, `cafe\w*`) because DuitNow QR names run words together ("RESTORANMAHBUB"). Cash withdrawals are **transfers** to the cash account; Touch 'n Go reloads are **expenses** (so they aren't double counted).
- Dedupe uses `importKey` (a fingerprint stored on the transaction) plus a one-to-one fuzzy match (same amount, within 2-3 days) so a transfer logged by hand is recognised from either account's statement.
- `commitRows` is all-or-nothing in one DB transaction, validates every row, remembers rules, and sets an opening balance only for an account with no transactions yet.
- Server actions are capped at 1 MB by default; `next.config.ts` raises it to 10 MB for statement uploads.
- **Page breaks (Maybank):** a row can straddle two pages, with its payee lines at the top of the next page under the column header. `parseStatementText` drops everything from the "Perhation / Note" footer to the next column header *without* ending the open row, so those lines still attach to it.
- **Adding a default category** needs BOTH a `seed.ts` entry (new databases) and a custom migration (`drizzle-kit generate --custom`) for existing ones. Migrations run BEFORE `seedIfEmpty`, so the migration must insert only `WHERE EXISTS (SELECT 1 FROM categories)` (and `NOT EXISTS` the same name), or a brand-new database would look "already seeded" and get none of the defaults. See `0003_*.sql` and its tests in `tests/db.test.ts`. A merchant rule in `builtin-rules.ts` falls back to Miscellaneous if its category is missing.
- **Amounts** may carry `RM` or `MYR` (CIMB's CSV: `MYR 150.00`); `parseMoneyToken` strips both. `fixSplitDecimals` repairs `MYR 25. 00` (cents laid out as separate text in a web page printed to PDF).
- **Web pages printed to PDF** (CIMB Clicks history) put each transaction over several lines with the date in the MIDDLE (head, date + amounts, tail). `extractPdfPages` keeps each line's height; `splitRowBlocks` groups lines into rows where the gap exceeds 1.8x the median line gap; `rowBlocksToLines` rebuilds one line per row. `buildPreview` uses that reading only when `blocksHaveHeads` (some row has text above its date line, which ordinary statements never do) and it finds at least as many rows, so it can't replace a good reading. Never pass `splitRowBlocks` straight to `.flatMap` (the index becomes its `factor` argument).
- **Direction from the page's own columns:** `amountColumns` reads the "Money In" / "Money Out" headings (first page only; the columns are the same on every page) and `blockDirection` says which column a row's amount sits under; `rowBlocksToLines` then marks the amount `+` or `-`, which the parser reads as a hint (`signedBy: "hint"`). That settles the OLDEST line too, which no balance chain can. It is the reason a friend's payment (nothing in its text says credit) was once saved as a Netflix purchase: guessed out, then matched to the bill by the word "Netflix".
- **The oldest row's direction** (no balance before it), for layouts without such columns: if `check.firstRowGuessed` and the books already hold the balance before that day (`booksBalanceBefore`), exactly one direction can reproduce the printed balance, so it is used and the guess flag cleared. If neither (or both) fits the books are out of step with the bank, and the guess stays flagged.
- **Starting balance** (`setOpeningBalance`) is allowed only when nothing on the account is dated *before the statement's first line* (`countEntriesBefore`, counting either side of a transfer). Counting all entries would block the second account of a pair, because importing the first mirrors transfers onto it.
- **Card pre-authorisations** (debit, then an equal refund from the same merchant) cancel to RM 0: `findCardHolds` (`holds.ts`) starts from the refund (its text says PRE-AUTH / REV PREAUTH) and skips both halves, source `"hold"`. Only pairs within one statement are found. A second pass in the same function pairs a `REV` / `REVERSAL` line (or Maybank's cut-off `PYMT VIA MYDEBIT RE`) with an equal, opposite line up to 3 days earlier (a failed transfer put back by the bank has no merchant to compare and different wording on each half); same source, so `stats.holds` counts both.
- **Bank wrapper words** (`IBK FUND TFR FR A/C`, `PAYMENT VIA MYDEBIT`, `DuitNow QR`...) are stripped by `stripBoilerplate` (`boilerplate.ts`; add a bank's wording to its `PHRASES`) before `rulePattern` and `cleanItem` run. Without that, every Maybank QR payment shared one group, so correcting one rewrote them all and `remember` saved a rule matching every QR payment. `rulePattern` returns `""` when nothing identifies the payee; such lines get a group of their own (`line-<index>`) and never become a rule.
- **Duplicate matching** (`classifyRows`, step 1): exact `importKey` first. Then fuzzy: an entry typed by hand matches within 2 days (transfers 3). An entry *imported from a statement* matches only on the SAME day (the next statement's RM 8 lunch is not yesterday's), and an imported *transfer* (mirrored from the other account) is matched only by a transfer-looking line (`TRANSFER_WORDS` and not a QR payment, or a name a learned transfer rule knows, so a layout that drops the bank's wording still matches). Loosening either silently drops real transactions. Known limit: two files whose dates differ by a day for the same transaction (value date vs posting date) are NOT recognised as the same.
- **The Add form does the same check the other way round** (`findLookalikes`, `src/lib/queries/lookalikes.ts`, served by the GET route `src/app/(app)/transactions/lookalikes/route.ts`; `TransactionForm` fetches it, debounced, for NEW entries only): it lists imported entries (`importKey` set; never hand-typed ones) of the same amount, direction and account within `LOOKALIKE_DAYS` (2; transfers 3), which are the importer's windows for a hand-typed entry, so change them together. It is a route handler, not a Server Action, on purpose: Next dispatches actions one at a time per client and they are meant for mutations, so a read-only lookup must not make Save wait. The result is stored with the query it answers (`looked.key`), so a stale answer is never shown for a changed amount.
- **"Use this one"** (`adoptLookalike`, `src/app/actions/transactions.ts`, a button in `TransactionForm`) puts the typed `item` and `categoryId` onto an imported lookalike instead of adding a second entry. Rules that matter: it re-runs `findLookalikes` on the server and only touches an entry that is still a current lookalike AND `adoptable` (plain spending/income, no `billId`/`shareId`; never a transfer), so a stale or forged id rewrites nothing; it never changes `date`, `amount`, `accountId`, `note` or `importKey` (a later import matches on the date, and `history.ts` learns each payee from `note`, so overwriting either would silently break both). The buttons are `type="button"` and dispatch through the SAME `useActionState` reducer as Save (`fd.has("adopt")`): a submit button listed above Save would become the form's default, so Enter in the amount box would adopt instead of add. The category/item you put on imported entries also feed `learnFromHistory`.
- **`startDate`** (`buildPreview`) leaves out earlier lines and takes the bank's balance just before the first kept line as the starting balance. Rows keep their original `index`, so their fingerprints equal a full import's.
- **`oneSided`** lists transfers present on only one account's statement (`where: "other"` = recorded from the other statement, absent here; `"here"` = here, but the other account is imported for these dates and has no mirror). It is the early warning for money that went to an untracked account. A `"here"` entry is only raised when the other account has imported activity within 3 days BEFORE and within 3 days AFTER the transfer: a transfer at the edge of a month whose other statement isn't imported yet (2 Jul when only June and August are in) is not judged.
- **Touch 'n Go eWallet history** (`tng.ts`, called from `buildPreview` before the generic reader): the "TNG WALLET TRANSACTION HISTORY" PDF is a table turned on its side (one COLUMN per transaction, one ROW per field at fixed heights from the date row, wrapped cells in pieces ~12 apart), in TWO tables: the wallet's, then GO+ (a sweep account that pays a fraction of a sen a day). The "GO+ TRANSACTION" heading appears on one page; every column right of it and on later pages is GO+. Wallet <-> GO+ moves (`eWallet Cash Out`, `Reload ... via GO+ Balance`, `GO+ Cash In`) cancel out, so they are NOT lines; a `Payment` with status Reversed plus its `Payment Cancelled` credit cancel too (unpaired, they stay as lines). `Transfer to Wallet` is money OUT to a friend. Only DuitNow receives, payments, sends and one GO+ interest line remain. There is no per-line balance, so `BalanceCheck.total` carries a whole-statement check: opening (each table's balance before its first line) + lines = closing (each table's last balance), to the sen; the interest line is the residual if it is within 2 sen of the summed daily fractions. Unknown line types are left out with a warning and the check then fails. Rows get derived running balances (so `startDate` cuts and `accountCheck` work). The wizard shows "These lines take the account from X to Y" instead of the running-balance banner. Import banks BEFORE the wallet, so its DuitNow credits are recognised as the bank-side transfers already recorded; track the wallet from a statement's first day with that statement's opening balance (earlier top-ups stay `E-wallet top-up` spending).
- **Quiet accounts (Maybank MAE layout):** dates read `31/07` with the year only in the statement date (`inferYear`), and a month with one transaction (or none) puts the column headings, `BEGINNING BALANCE` and the whole table in ONE block. `blocksHaveHeads` therefore ignores blocks whose lines above the date are column headings or an opening-balance line; otherwise the print-out reader replaced the correct reading with the headings. A month with no transactions and opening = closing balance returns "This statement has no transactions: the balance stayed at RM X" instead of a layout error.
- **`accountCheck`** (wrong-account guard): when the account already has entries before the statement and the opening balance can be trusted (stated, the bank's own balance before a `startDate` cut, or a first line whose direction was read rather than guessed), `preview.ts` compares it with `booksBalanceBefore`. A difference sets `accountCheck`; `looksLike` names another account whose books equal the statement's opening exactly, which almost always means the file was uploaded for the wrong account (the wizard then offers a one-click re-read as that account and requires a tick to import anyway). A difference with no twin usually means an earlier month isn't imported yet.
- **Remembering a transfer destination never re-points an existing transfer rule** (`commitRows`): an own-name payee ("FABIAN A/L LESLIE") goes to several different accounts, so one correction ("this one went to the e-wallet") must not flip the rule that sends the rest to the other bank. Everything else is still "latest decision wins".
- **Cross-account transfers:** a learned transfer rule names the OTHER account, so one pattern can't point both ways. Own-name transfers are not necessarily to the other bank: check `oneSided`.
- Tests build **real PDFs** (`tests/pdf-fixture.ts`) rather than mocking the extractor. Real Maybank/CIMB layouts are untested; when one fails, add a fixture that reproduces its layout.

## Phone app (PWA over Tailscale)

- **Pieces:** `src/app/manifest.ts`, the icon routes `src/app/pwa/*` (drawn by `src/lib/pwa-icon.tsx`), `public/sw.js` + `public/offline.html`, `ServiceWorkerRegister` (production only, mounted in the root layout), and `start:phone` / `scripts/start-phone.cmd` (listens on 127.0.0.1:3100 only; `tailscale serve --bg 3100` is the single door in). The user-facing steps are in the README.
- **Offline = saved pages + an outbox for NEW entries; nothing else works without the PC.** Reading: `public/sw.js` keeps every page as last seen and shows it when the PC doesn't answer. Writing: new income/expense/transfer entries go through the phone's outbox and sync later. Changing or deleting a saved entry, import, settings, shared bills, investments and the cash count all need the PC: they say so and change nothing (the form turns the failed fetch, a `TypeError`, into a message).
- **The outbox (`src/lib/offline/`).** `types.ts`; `outbox-store.ts` (`OutboxStore`: IndexedDB on the phone, `memoryStore()` in tests); `sync-engine.ts` (`syncOutbox`: batches of 25, files each verdict); `offline-store.ts` (`createOfflineStore(deps)`: the observable state and every action; NO browser access, storage, network and clock are injected, so it is tested in plain Node); `browser.ts` (the real bindings: fetch with timeouts, the `/ping` probe, localStorage, Web Locks, the app badge, messages to the worker; the singleton `offlineStore()`); `ids.ts`. Screens in `src/components/offline/`: `OfflineProvider` (starts the watching, in `(app)/layout.tsx`), `SyncChip` (header badge), `SyncBanner`, `OutboxList` (Retry / Edit and retry / Discard), `AddEntry` (remounts `TransactionForm` with a `draft` to correct an entry), `LockNowForm`. `TransactionForm`'s create path calls `store.submit` / `store.update`; editing a saved entry and "use this one" still call Server Actions.
- **Rules that matter (each has a test).** (1) Store BEFORE send: an entry is written to the phone's storage first, then sent, so an app killed mid-send loses nothing. (2) Every entry carries a `clientId` (a UUID made on the phone; unique index `transactions.client_id`, migration 0007), so sending twice can never make two rows: the PC answers `duplicate`. (3) A refusal of a brand-new entry goes back to the form and is NOT queued; a refusal during a background send, or of a corrected entry, leaves it `failed` with the PC's reason, and a failed entry is NEVER resent until the user taps Retry or Edit and retry. (4) "Can't reach the PC", "wants the PIN again" and "the PC errored" are not failures: entries stay `pending`. (5) The PC judges phone entries with the same `checkEntry` (`src/lib/entries.ts`) as the form's Server Action, and `entryShapeError` (`src/lib/entry-shape.ts`, no database) runs on the phone first; change a message and the old tests say so. (6) Correcting an outbox entry keeps its `clientId`. (7) `useSyncExternalStore` takes a CONSTANT `getServerSnapshot`, so the first paint equals the server's and nothing mismatches. (8) The form's default date is `pickedDate ?? todayISO()` read from the device's clock, because a saved page's `defaultDate` may be yesterday's.
- **The worker (`public/sw.js`).** Pages are network-first: it waits 4 s for the PC (0.8 s once the app has sent `pc-gone`; `pc-back` resets, and it forgets after a minute), then shows the saved copy. A saved copy is stamped `x-saved-at` and served with `<script>window.__MT_SAVED_AT=...</script>` injected before `</head>`, so the store can say "this page is a copy, from then" and refresh it the moment the PC answers (React 19 hydrates it fine). `/_next/static/*` is cache-first; `/pwa/*` and the manifest are network-first. Messages: `save-pages` (fetch each tab and the scripts it names, spelled both `/_next/static/...` and `static/...`; stops at the first silence), `forget-pages` (Lock now), `pc-gone` / `pc-back`. A reverse proxy answering 502/503/504 (`tailscale serve` after a PC restart, before anything has started the app: Go's default proxy error) is SILENCE, not an answer: `gatewayFailure` in the worker and `isGatewayFailure` in `src/lib/offline/network.ts` (used by `post` and `probe`), because otherwise the phone shows the proxy's "Bad Gateway" and thinks the PC is there; the app itself never says these, and its own 500 is never hidden. It must never touch non-GET requests, RSC/data fetches, `/ping`, `/sync/entries` or lookups. When a client-side navigation's RSC fetch fails, Next falls back to a plain browser navigation (`experimental.useOffline` is off), which is why tapping a tab offline reaches the worker. Bump `VERSION` when you change the caching rules or `offline.html`.
- **Routes.** `POST /sync/entries`: JSON only, cross-site refused, at most 50 entries, one verdict per entry (`saved` | `duplicate` | `rejected` + reason). `GET /ping`: needs `connection()`, because Next would otherwise bake a constant reply into the build (and cannot represent an empty 204 at all).
- **Security.** The phone now keeps copies of your pages (the worker's cache) and unsent entries (IndexedDB). The PIN gates the server, not those copies, which matches the existing 30-day cookie model; the phone's lock screen is the protection. `Lock now` (`LockNowForm`) forgets the saved pages; unsent entries stay and go after the next sign-in.
- **`src/proxy.ts` must keep excluding** `manifest.webmanifest`, `pwa/`, `sw.js` and `offline.html` from the PIN lock: a browser fetches them without the login cookie, and a redirect to `/login` would be cached as "the offline page". `tests/pwa.test.ts` guards this, the manifest's install criteria, and runs the real `sw.js` in a stand-in worker environment.
- **Facts checked against sources (Oct 2026):** `tailscale serve` keeps the original `Host` and sets `X-Forwarded-Host` (tailscale `ipn/ipnlocal/serve.go`), so Next's Server Action origin check passes with no `serverActions.allowedOrigins`; if actions ever fail with "Invalid Server Actions request" behind a proxy, that setting (the host as shown in the address bar) is the fix. Chrome's install criteria (web.dev) no longer list a service worker: HTTPS + manifest (192 and 512 PNG icons, `start_url`, `display: standalone`) is what makes it installable. Setting up Tailscale HTTPS publishes the machine's name in public certificate logs.

The Claude desktop app's in-app browser pane cannot register service workers (its network layer refuses the script fetch, with no request reaching the server), so don't debug them there. The real proof is a real Chromium: headless Edge/Chrome with a throwaway `--user-data-dir`, driven over the DevTools protocol from Node against a PRODUCTION build and a scratch database. That is how the whole story was verified: pages saved after login, an entry saved online, the PC off, saved pages hydrating (no hydration errors), entries queued and surviving a reload, the PC back and the sync, a refused entry, Edit and retry, Retry, Discard, a duplicate send, a sleeping PC (a TCP socket that accepts and never replies: 4 s the first time, under a second once the app has noticed) and Lock now. Pitfalls met: assert on the database, or on something that cannot be stale (a "Sent" notice from the PREVIOUS sync is still on screen for 6 s); and run it on a port other than 3100, where the user's real `start:phone` server may be listening (the harness's own server then fails to bind but its readiness check still gets an answer, so it quietly drives the real one). `tests/offline-network.test.ts` covers `post`/`probe` (verdicts, login redirect, errors, gateway failures, hangs).

## Personal data stays out of the repo

The user's real setup (accounts, bills, income) is loaded by a throwaway script **outside the repo** (session scratchpad), run against `data/finance.db` (gitignored). Don't put real names, amounts, bank statements or PDFs in the repo, tests or docs; tests use generic bill names and invented figures (a few round scenario numbers like a RM 5,400 salary are fine; a real person's full bill list is not).

## Editing hazard on this machine

Scripted string rewrites through shell heredocs / `node -e` swallow backslashes (a `\b` regex became a literal backspace character, 0x08). Edit regexes and anything with backslashes with the Edit/Write tools, never with a script; after any scripted edit, grep for control characters.

## Analytics conventions

- `src/lib/analytics/*` and `src/lib/investing/*` are **pure** (rows in, numbers out; no DB, no clock). Keep them that way and unit-test them.
- Leak detection compares **like-for-like** (days 1..today vs the same days in earlier months). Linear extrapolation wrongly flags fixed bills like rent. A single big purchase is flagged but never annualised into a "saving".
- A baseline month counts only if the data covers it **from day 1** (`dataStart <= month-01`). Data that starts on the 26th would otherwise make the month before look nearly empty and every category look like "creep".
- Mid-month KPI comparisons use the previous month's same days, not the full month.

## Testing

`tests/db.test.ts` and `tests/actions.test.ts` run the real SQL and the real server actions against an in-memory SQLite DB; only Next's `redirect`/`revalidatePath`/`@/db/client` are stubbed. Add a test there for any new action.
